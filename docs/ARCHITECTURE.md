# Architecture

## P0: establish a truthful, testable foundation

```
React + TypeScript
       |
       | HTTP / JSON
       v
FastAPI
       |
       +-- Project metadata (SQLite)
       +-- Original audio (local storage)
       +-- Analysis adapter (not implemented yet)
       +-- Canonical Drum Events model (next phase)
```

## Canonical event model (planned)

All editing and exports should share one canonical event representation. A future event should include:

- stable event ID
- time in seconds and/or sample position
- bar, beat, and subdivision when tempo mapping is available
- instrument identifier (kick, snare, closed/open hi-hat, ride, crash, toms)
- MIDI velocity
- confidence score (when generated by a model)
- source/model metadata
- whether the event was manually corrected

Tempo maps and time-signature changes must be representable; a single fixed BPM assumption is not sufficient for every song.

## Engine boundary

The API must call an engine adapter rather than importing a specific transcription implementation throughout the web layer. This allows controlled comparison of candidate engines and makes it possible to replace a weak model without rewriting project management or the editor.

## Notation and editing

OpenSheetMusicDisplay renders MusicXML. It is not, by itself, a complete interactive drum notation editor. The editor will need its own event/grid interaction layer and must update the canonical event model.

## Export

MusicXML is the interchange/notation representation. MIDI and PDF must be generated from the same canonical events so edits remain consistent across formats.

## Non-functional requirements

- Validate file extension, MIME type, and size.
- Generate server-side project IDs; never trust client paths.
- Keep uploaded audio outside the public frontend directory.
- Add cleanup, quotas, and authentication before public deployment.
- Do not expose arbitrary filesystem paths through API responses.
